# dsh 0.1.7-rc.1 适配评估

> 历史快照：本文记录 2026-09-24 的调查结论与当时的仓库状态，不是现行兼容说明；其中的版本号、HEAD、发布状态和“尚未完成”的判断都停留在该时点。现行支持边界见 [README](../README.zh-CN.md) 和 [DESIGN](../DESIGN.md)。

核对日期：2026-09-24。仓库基线：main `3f16de5`；上游固定线：npm 已发布 `@deepseek-ai/dsh@0.1.7-rc.1` 及同 family 全部 `0.1.7-rc.1` 包（npm `next`；`latest` 仍是 `0.1.5-rc.3`）。

## 结论

可以把本仓库从 dsh `0.1.5-rc.2` 升级到 `0.1.7-rc.1`，建议下一版为 **`0.1.7-rc.1-v0.1`**（版本号跟随上游宿主，规则见 README「先选对版本」与 `docs/development.md`；这是 0.1.7 线启用的新规则，不再使用 `0.8.x` 序号）。这不是一次纯依赖升级：

- **设置架构被整体替换**。`ctx.settings.installSection(...)` 及配套的 `SettingsProvider`/`SettingsScope`/`SettingsSectionHooks` 在 0.1.7 中不存在，改为「插件配置由 profile patch 派生 + volatile 字段」：Loader 在只改动 volatile 字段时就地更新运行中的配置引用，写入前由 `dsh-config-editor` 用插件完整 Config schema 校验。
- **消息词汇表变更**。`tool-result` 不再是内容块，工具结果变成 `role: 'tool'` 的一等消息（`ToolResultMessage.toolCallId`）；新增 `developer` 角色与 `tool-addition`/`tool-removal` 块；`MessageSourceMap.plugin` 被 `system-prompt` 取代；`GenerateOptions.messages` 接受 request-only 的 `RequestUserInput`。
- **会话格式 V3 → V4**（`@deepseek-ai/dsh-session` 的 `SESSION_FORMAT_VERSION` 由 3 升到 4），用户升级宿主时需按上游迁移说明操作。

本插件真正接触的接缝面（LLM adapter、模型发现、凭据、超时、launch environment、connection RPC、客户端 slots/remote）中，运行时导出基本稳定：`@deepseek-ai/dsh-llm` 只新增 `IMAGE_OFFLOAD_REQUIRED_CODE`/`createDeveloperMessage`/`projectOffloadedImages`/`requiredImageOffload` 并移除本插件未使用的 `offloadRequestImagesWithPolicy`/`offloadedImagePrefixCount`；`dsh-credentials`、`dsh-timeout`、`dsh-launch-environment`、`dsh-client-ui-renderer`、`dsh-client-ui-slots`、`dsh-brand` 的运行时导出面与本插件用到的类型均无变化。适配工作量集中在 `src/index.ts`（设置接入与配置读取）与 `src/serialize.ts`（tool-role 消息）。

**合并判定：改动已完成类型、构建、组件测试、宿主兼容与 Cordis 组合测试；真实宿主启动验证（testbed L1+L2）结果见下文「本次实际验证」。本轮仍不晋升正式版。**

### testbed 实测

在本机 Docker（Engine 29.6.1 / Compose v5.3.1）上执行：

```sh
cd testbed
docker compose run --rm --build testbed     # DSH_VERSION 默认 0.1.7-rc.1，PROFILE_MODE=minimal，STEPS=all
```

结果（容器日志逐项）：L1 的 `npm ci`、host + client typecheck、build 后产物新鲜度比对、vitest、host-compat、smoke 全部通过；L2 启动真实 `dsh web` 后，一次性 token 换会话 cookie、首页 200、boot 图包含 `dsh-llm-newapi/client.js`、`/llm-newapi` RPC 通道以 unknown-endpoint 语义应答（HTTP 200）、日志卫生检查全部通过，`[testbed][0.1.7-rc.1][local][done] 所选步骤完成：STEPS=all`。

版本号切到 `0.1.7-rc.1-v0.1` 后重跑同一套流程：`npm pack` 产出 `dsh-llm-newapi-0.1.7-rc.1-v0.1.tgz`，pnpm 成功安装（`+ dsh-llm-newapi 0.1.7-rc.1-v0.1`），L1 + L2 再次全部通过——带连字符的跟随式版本号不影响打包、安装与 profile 装配。

需要注意 testbed 覆盖的边界：L2 只做 HTTP 探针（认证、boot 图、通道应答），不驱动浏览器交互，也不访问真实网关或 models.dev；设置页的保存、发现与凭据写入仍需人工在浏览器中确认（见存疑项 5）。

本机容器出口连不上 `deb.debian.org`（宿主可以），而 `apt-get update` 对「部分索引失败」仍返回 0；因此 `testbed/Dockerfile` 改为以 install 失败触发 apt 镜像回退。这是让 testbed 能在受限网络下运行的最小改动，与另一条进行中的「全球/中国双网络配置」计划（见存疑项 7）不冲突。

### 适配过程中的关键实验

1. **volatile 形态确认**：用最小脚本验证 `Schema.volatile()` 的 validate 输出是 `{ get, [write] }` 引用对象，且 `updateVolatile` 会就地更新；随后用真实 cordis `ctx.plugin` 验证插件 `apply` 收到的 config 字段即该引用。
2. **写入校验位置确认**：阅读 `dsh-config-editor` 的 `edit`，确认写入前执行 `resolveConfig(fiber.runtime, …)`（完整 Config schema），因此把校验搬进 schema 才能保持「写入点拒绝」。
3. **schema transform 的 options 陷阱**：schemastery 的 `transform` 回调实际只收到 value（实现 `callback(result)`），类型声明里的第二参数 `options` 运行时是 `undefined`；因此自定义 `ValidationError` 不能携带 path，错误消息本身必须点名字段（已如此处理）。
4. **apt 源回退**：本机容器内 `deb.debian.org` 连接被拒，而镜像源可达；`apt-get update` 对部分索引失败仍返回 0，因此 Dockerfile 以 install 失败触发回退（见改动清单）。

## 存疑项与待人工决策

1. **版本号与发布面已按维护者要求重整**：0.1.7 线起版本号跟随上游宿主——`<dsh 版本>-v<本插件序号>`，tag/Release 为 `v<插件版本>`。仓库最终只保留两条适配线：`v0.1.5-rc.3-v0.1`（npm `latest`）与 `v0.1.7-rc.1-v0.1`（npm `next`）；0.1.5 线以新版本号重新发布（内容等同原 `0.8.6-rc.3`，tag 指向专门的发布提交，其 `package.json` 与 npm 包一致），旧 `0.8.x` 的 tag 已删除、npm 上标记 deprecated。CI 已按同一约定实现：`v0.1.5-*` 发布到 `latest`、其余 rc 到 `next`，所有 rc tag 均为 Pre-release；旧线 tag 跳过 `boot`（固定宿主 0.1.7 会按版本 guard 拒绝旧线代码），`latest` 重认领步骤已移除。正式版规则已确定并实现：stable tag 形如 `v0.1.7-v0.1`（去掉宿主段 `-rc.N`），走 npm `latest` 与正式 Release；`promote` workflow 在已通过 CI 的 rc 提交上生成只改版本号的发布提交（刻意不推送 main），再触发发布。剩余边界：npm 禁止绕过 2FA 的 granular token 执行 unpublish，历史版本只能 deprecate 而不能删除。
2. **`loader/volatile-update` 事件未被使用**：0.1.7 的 Loader 会在 volatile-only 提交后就地更新引用并 emit 该事件。本插件改为在 `options()` 读取时检测重试策略变化（效果等价：注册表只在请求路径上被读取），代价是「设置变化到下一次读取」之间注册表仍是旧策略。如果希望恢复「变化即替换」语义，需要引入 `@deepseek-ai/cordis-plugin-loader` 的类型并监听事件——本次为最小依赖选择不做。
3. **`configure({ auto: false })` 的时机**：本插件在 `ctx.inject(['settings'], …)` 内注册策略，与官方 `dsh-client-ui-settings`/`dsh-client-locale` 的写法一致；未在真实 Web 设置页确认「不会出现重复的自动生成页面」。
4. **设置写入的落点与旧 `settings.yaml`**：0.1.7 由 `dsh-settings` 在启动后一次性导入遗留 `settings.yaml`（按 entry id 映射，未命中会留在重命名文件中）。本插件的旧段名 `llm-newapi` 与 entry id 相同，预期能被导入；但本次未构造遗留文件实测该路径。
5. **浏览器半边的真实联调**：客户端组件测试与类型检查通过，客户端 bundle 的模块工厂格式与 0.1.5 相同；真实 Web 中的设置页加载、保存、发现与凭据写入需要 testbed L2 或人工联调确认（见验证小节）。
